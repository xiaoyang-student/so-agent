# 编排运行时与高风险动作审批门

本文描述两处新增边界：编排运行时选择（原生默认 / 可选 LangGraph）与
工具调用前的高风险动作审批门。二者都不改变现有分阶段状态机、计划 /
执行 / 汇总协调器与人工兜底语义。

---

## 1. 编排运行时

### 1.1 协议

`so_agent.runtime.orchestration_runtime.OrchestrationRuntime` 只约定三个
生命周期方法：

```python
class OrchestrationRuntime(Protocol):
    name: str
    async def run(objective, constraints="", acceptance_criteria="") -> OrchestratorOutput: ...
    def cancel() -> None: ...
    async def wait_for_provisional() -> OrchestratorOutput | None: ...
```

`NativeRuntime` 直接委托 `WorkflowEngine`，是默认实现。CLI 完整工作流、
Web 任务与 `TaskRouter` 兜底路径都通过
`create_orchestration_runtime(engine, settings)` 获取运行时，因此选择点
只有一处。

### 1.2 LangGraph 适配器

配置：

```yaml
orchestration_runtime: langgraph
```

`LangGraphRuntime` 在构造时惰性导入 `langgraph`，用单节点 `StateGraph`
托管一次任务调用，节点内部仍调用原生 `WorkflowEngine`：

- 只是外层调用壳，不重写计划/执行/汇总，不改变 HITL 与检查点；
- `checkpointer` 与 `thread_id` 原样交给 LangGraph，适合已有 LangGraph
  基础设施的团队；
- 未安装 `langgraph` 时 CLI 以退出码 2 拒绝启动，Web 抛出
  `RuntimeError`，不会静默回退到 native；
- 内核不依赖 LangGraph，默认安装与运行不需要该包。

限制应明确：当前适配器不把 13 阶段状态机映射为多个图节点，因此
LangGraph 的节点级暂停/恢复不会替代内核的人工兜底与检查点。

## 2. 高风险动作审批门

### 2.1 开关与位置

默认关闭：

```yaml
high_risk_approval_enabled: false
high_risk_approval_timeout_seconds: 300
high_risk_approval_poll_seconds: 1.0
high_risk_approval_patterns: ""      # 追加正则，分号分隔
approval_store_path: ""              # 空 -> 共享存储目录/tool_approvals.db
```

启用后，`code_agent` 的 `run_in_sandbox` 在真正执行前先做确定性风险
评估。内置风险模式覆盖：`os.system` / `os.popen`、`subprocess`、
`shutil.rmtree`、`socket.`、`requests` / `httpx` / `urllib.request` /
`http.client` / `aiohttp`、`curl` / `wget`、`rm -rf`、`chmod 777` /
`sudo`、`git push`、`mkfs` / `format` 盘符。命中即要求审批。

未命中风险模式时行为与未启用完全一致，不创建审批库、不增加等待。

### 2.2 流程

1. 评估命中 → 计算幂等键 `sha256(task_id | tool | 参数摘要)`；
2. 在 SQLite `tool_approvals` 落盘记录（同一键只创建一次）；
3. 新建记录时投递通知：复用人工升级的 `EscalationNotifier`，事件类型
   `tool_approval_required`；启用 outbox 时先入队再由后台任务排空，
   `event_id` 即审批编号，接收方可按 `Idempotency-Key` 去重；
4. 轮询等待决定，超时或拒绝即返回错误给模型（不抛穿任务）：
   `{"status":"error","approval_required":true,"error":"高风险动作未获批准…"}`；
5. 批准后执行沙箱调用；审计事件写入
   `tool_approval_requested` / `tool_approval_granted` /
   `tool_approval_denied`。

审批记录只保存参数摘要、命中标签与字符数，不保存代码或参数原文。

### 2.3 决策通道

Web 控制台 API（与其他运维接口使用同一鉴权依赖）：

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/approvals?status=pending&task_id=` | 列表（`status` 传空串表示全部） |
| `GET /api/approvals/{approval_id}` | 单条详情 |
| `POST /api/approvals/{approval_id}` | `{"approved": true/false, "reason": "..."}` |

已处理或已过期记录再决策返回 409；不存在的编号返回 404。

通知 Webhook 只负责送达，决策仍以 Web API 为准。CLI 运行同样落盘，
但没有内置交互式审批命令；生产建议启用 Web 控制台或接入审批前端。

### 2.4 与 Web 重启恢复的关系

审批库位于跨任务共享存储目录（Web 为 `persistent/`，CLI 为任务
`task_store_dir` 或 `sandbox_dir`），进程重启后记录仍在：

- 重启后 Web 仍可列出并决定历史待决记录；
- Web 的任务自动恢复会以同一 `task_id` 重跑；若模型再次发起相同工具
  调用，幂等键相同，会复用已有记录（已批准则直接放行，已拒绝则继续
  拒绝，待决则继续等待），不会重复通知或重复创建审批；
- 自动恢复从任务级重新执行，不是工具调用级断点续跑；模型重新生成的
  参数不同则视为新审批。

### 2.5 安全边界与限制

- 风险判定是确定性正则，不是语义分析；未命中模式不代表动作安全；
- 默认关闭是为了避免在未配置通知/审批通道的部署中阻塞任务；开启后
  必须确保有人或系统能处理待决记录，否则超时按拒绝处理；
- 审批库写入失败、等待异常、超时均 fail-closed；
- `permissions` / 审批门都不是操作系统级隔离；不可信代码仍需容器或
  microVM 沙箱。
