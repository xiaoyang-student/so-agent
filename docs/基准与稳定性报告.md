## 0. 结论摘要

1. **简单任务可稳定完成**：单子任务探针 62.81s / 42,931 tokens，产物已真实写入并回读验证。
2. **复杂任务未完成**：5 步销售分析在 900s 外部观测上限内被取消，消耗 **265,010 tokens / 25 次模型调用 / 4 次工具调用**（其中 1 次失败被取消），仅完成 2/5 子任务，`summary.json` 与 `report.md` 未产出。
3. **同任务原生 API** 单次调用 290.04s / 21,538 tokens，五步内容完整；离线落盘执行后数据一致。
4. **同任务 AI Studio 网页** 约 350s，四件产物完整；离线落盘执行后数据一致。
5. **成本结构失衡**：65.7% 的 token 花在 `code_agent`；其中规划阶段两次并行调用的 46,616 tokens 全部作废，执行阶段 ST-001 又以 597s / 127,453 tokens 重做。
6. **生产侧 token 台账失真**：只记录 82,765 / 265,010（31.2%），嵌套 `code_agent` 的 174,069 tokens 完全未入账。
7. **“子 Agent 重试”主要是内部自纠错，不是调度器重试**：ST-001 只被调度 1 次，但内部跑了 7 轮模型调用；根因是工作目录语义不一致、工具校验失败、输出无上限。
8. **总体判断（10-31 基线）**：简单任务可用；复杂任务的稳定性与成本效率不达标，问题以设计与实现缺陷为主，模型行为是放大器。建议先完成 P0 修复，再扩大任务复杂度。
9. **11-02 改造后复跑**：复杂任务首次在 903.1s 内完成并通过全部验收（369,667 tokens），但第二次超过 1000s 被外部取消（440,974 tokens），第三次 `passed=false`（509,326 tokens）。完成度改善成立，成本未下降，稳定性方差仍大；详见第 10、11 节。
10. **11-03 超时语义与成本改造**：改为“无进展看门狗（1200s）为主、总时长（2400s）仅兜底”，配套子任务检查点、续跑只补未完成项、工具输出截断与评审解析一次重试。同一任务复跑：run-2 在 **803.17s / 326,037 tokens** 完成且 14 项清单全通过，为目前最快、最低成本的完整通过；run-1 在 1800s 外部观测上限被截断（572,395 tokens），但截断前四件产物已齐全。**1000s 并非产品超时**，而是探针观测上限；任务本身重、模型分支方差大，固定总时长不能作为正常运行期的治理手段。详见第 14 节。

## 1. 测试方法与口径

### 1.1 测量手段

- 使用 OpenAI Agents SDK 的 `TracingProcessor` 采集所有 generation span，覆盖主管、`code_agent`、`review_agent` 及嵌套调用。
- 同时读取生产侧 JSONL 事件台账（`token_usage` 事件），用于对比“生产可观测性”与“真实消耗”的差距。
- 工具调用通过 `tool_called` 事件的 `invoke_started` / `invoke_completed` / `invoke_failed` 配对计算真实耗时。
- 时间为墙钟时间；复杂任务外部观测上限为 900s。项目自身 `max_pipeline_timeout=2400s`，因此 900s 是**观测上限**，不是产品硬上限。

### 1.2 任务内容

1. 生成 `sales.csv`（≥36 行，字段 `date,region,product,quantity,unit_price`，覆盖 2026-01 至 2026-06、3 地区、3 产品）；
2. 编写 `analyze_sales.py`，按地区、产品汇总销售额，计算总额与最高产品；
3. 运行脚本生成 `summary.json`（`total_sales/by_region/by_product/top_product`）；
4. 根据 `summary.json` 编写 `report.md`；
5. 用 `read_file` 回读 `report.md` 与 `summary.json`，核对关键数字一致。

### 1.3 公平性说明

- 原生 API 与 AI Studio 网页没有文件系统或代码执行工具，只能输出文本内容；其产物由我离线落盘并真实执行验证。
- SO-Agent 会真实写文件、真实运行脚本，二者不是逐字节同构对比。
- 对比重点是：**完成度、数据一致性、总耗时、token 消耗、稳定性**。
- 网页端不暴露 token 用量；网页耗时由消息时间戳估算（15:39:58 → 15:45:48）。

## 7. 子 Agent 重试与失败根因

### 7.1 先区分两类“重试”

| 类型 | 本次是否发生 | 证据 |
| --- | --- | --- |
| 调度器级重试（同一子任务多次 `task_dispatched`） | **没有** | ST-001、ST-002 各只有 1 次 `task_dispatched`，`attempt=1` |
| `code_agent` 内部自纠错（一次调度内多轮模型调用） | **发生** | ST-001 内部 7 次模型调用；输入从 3,318 涨到 25,592 |

因此，用户观察到的“子 Agent 重试”主要是**工具失败后的模型自纠错**，而不是框架在反复重派子任务。

### 7.2 根因排序

1. **工作目录/相对路径语义不一致（首要）**
   - `run_in_sandbox` 每次调用在独立任务目录执行，而 `write_file` / `read_file` 以沙箱根目录解析相对路径。
   - 结果是“脚本写到了 A 目录、校验在 B 目录找”，模型看到失败后重写、重跑。
   - 历史证据：`fix_check_exists_in_cwd=false`，随后重试在 10.031s 内成功，说明失败并非能力问题，而是路径约定问题。

2. **工具返回的校验信息不足以一次修正**
   - 校验失败时，模型需要多轮猜测；如果错误信息只给“失败”而不给期望路径/字段，就会重复试错。
   - 复杂任务中 ST-001 的 7 轮调用与此吻合。

3. **单轮输出与上下文无上限**
   - 最后 3 轮分别输出 6,311、3,633、14,913 tokens；输入涨到 25,592。
   - 长输出既拖长时延，也让后续轮次更贵，形成正反馈。

4. **规划期允许高成本工具且允许并行重复**
   - 模型在 planning 阶段直接调用 `code_agent` 两次，且并行执行；两次都产出后被弃用。
   - 框架没有“同阶段同参数调用去重”，也没有“规划阶段工具预算”。

5. **评审轮次固定且契约较宽**
   - 简单任务也要 4 次 review；复杂任务 6 次 review。
   - 评审输出偶有 schema 偏差，需要额外轮次修正。

6. **模型行为放大**
   - MiMo 倾向“先做再说”，在规划阶段就动手；输出偏长；对失败的自纠错耐心较高。
   - 同样的探针提示，模型一次规划 1 个子任务、一次规划 2 个，导致 62.8s vs 195.8s 的差异。

### 7.3 能否减少失败

可以，且大部分是确定性修复，不依赖换模型：

- 统一工作目录语义后，路径类失败应大幅下降；
- 规划阶段禁止直接执行型工具（或要求显式工具缺口声明）后，重复工作会消失；
- 给子任务设置模型调用数/输出 token/墙钟硬预算后，失控轮次会被快速终止；
- 工具返回结构化、可操作的错误（期望路径、缺失字段、修复建议）后，自纠错轮次会减少；
- 评审分级后，小任务的固定开销会下降。

具体降幅需要修复后复测，不在本报告提前承诺数字。

| 规划结果不稳定 | 模型 | 同题 1 vs 2 子任务，62.8s vs 195.8s | 中 |
| 输出冗长、规划期急于动手 | 模型 | 长脚本、长自检、规划期工具调用 | 中 |
| 自纠错轮次多 | 模型 + 设计 | ST-001 7 轮；错误信息不够可操作 | 中高 |

总体判断：**设计与实现因素占主导，模型行为是放大器**。仅换更“听话”的模型可以缓解，但不能消除路径、预算、台账这些结构性问题。

## 9. 改进建议（基线评审用）

> 11-02 更新：路径语义统一、规划期工具确定性拦截、token 全链路归因、写作用域校验等 P0 项已落地并在同一任务上复跑（见第 10 节）；子任务硬预算、完整多维预算与上下文治理仍未实施。本节保留 10-31 基线时的原始建议与口径。

### P0：稳定性与可观测性（优先）

1. **统一工作目录语义**
   - `write_file` / `read_file` / `run_in_sandbox` 全部以显式 `workspace_dir` 为根；
   - 子任务启动时把工作目录写入工具输入与提示词；
   - 禁止依赖进程 cwd 的相对路径命令。

2. **规划阶段工具白名单与调用去重**
   - planning 阶段只允许规划类输出；如需补工具，走显式“工具缺口声明”，由控制层创建；
   - 同一阶段相同工具 + 相同参数只允许一次，重复调用直接复用结果或拒绝。

3. **子任务硬预算与快速失败**
   - 为每个子任务设置最大模型轮次、最大输出 tokens、最大墙钟；
   - 超限立即失败并输出诊断，不再让内部循环无限自纠错。

4. **全链路 token 台账**
   - 把嵌套 `code_agent` / 动态子 Agent 的 usage 写入 `token_usage` 事件；
   - Web 路线图与任务详情展示真实成本。

5. **输出与上下文上限**
   - 对 `code_diff`、脚本、日志做截断/摘要后再回传主管；
   - 超过阈值时强制压缩上下文，避免输入指数增长。

### P1：效率与体验

6. **评审分级**
   - 单子任务/低风险计划跳过计划评审，仅保留结果校验；
   - 授权评审与计划评审批量合并，减少重复轮次。

7. **复用与检查点**
   - 规划阶段产生的可用产物登记为检查点，执行阶段优先复用；
   - 长任务按子任务落盘，超时后可从未完成子任务续跑。

8. **模型分级路由**
   - 规划与高风险评审用强模型；简单执行子任务用更快/更便宜的模型；
   - 降低 `max_model_turns`，用确定性脚本替代模型自检。

9. **提示词与契约收紧**
   - 明确“规划阶段不得调用执行型工具”“单轮输出上限”“失败时先报告而不是反复试错”；
   - 评审输出使用更严格的 JSON 契约与示例，减少 schema 修正轮次。

### P2：长期治理

10. **增量验收**：每完成一个子任务立即验收并落盘证据，而不是最后统一汇总。
11. **成本预算与告警**：按任务设置 token/时间预算，接近阈值时告警或降级。
12. **基准回归**：把本次三组对照固化为回归基准，任何优化后复跑同一任务对比。

- 900s 是本次观测上限，项目允许 2400s；因此“超时”应表述为**在 15 分钟观测窗内未完成**，而不是产品必然失败。

## 14. 11-03 超时语义改造与复跑

### 14.1 为什么会出现 1000s

- **1000s/1800s 是探针的外部观测上限**（`asyncio.wait_for`），不是产品超时；当时的 `max_pipeline_timeout=2400s` 仅为绝对兜底。11-03 继续迭代后，所有任务级总时长（`agent_total_timeout` / `supervisor_total_timeout` / `max_pipeline_timeout`）默认改为 `0`（关闭），只保留存活/活动检测。
- 任务本身确实重：同一任务的 `code_agent` 生成耗时 run-2 为 467.6s，run-1 为 1001.1s；5 个子任务串行执行，叠加计划/结果两轮评审。
- 设计放大项：结果评审返工、工具失败后的恢复重试、单轮输出过长。run-1 中 st5 先后经历契约解析失败与沙箱失败两次恢复，结果评审又要求 st3 返工，执行阶段持续约 1496s。
- 因此“超过 1000s”应拆成两件事：任务在正常推进时耗时不可预测；真正需要治理的是**长期无进展**和**失败重试放大**，而不是给正常运行设一个固定总时长。

### 14.2 本次改造

| 项 | 改造内容 |
| --- | --- |
| 超时主控 | `pipeline_no_progress_timeout=1200s`：连续无活动才判定停滞并转人工；SDK 流事件、工具生命周期、子任务完成、阶段推进、检查点落盘都会续期 |
| 总时长 | 任务级总时长默认 `0`（关闭）：`agent_total_timeout`、`supervisor_total_timeout`、`max_pipeline_timeout` 均不再管制正常任务；部署方仍可按需显式开启绝对兜底，开启后由 `PipelineDeadlineExceeded` 防止被宽捕获误判 |
| 检查点 | 子任务级落盘；超时/取消保留已完成结果，续跑只补未完成子任务 |
| 续跑入口 | 已恢复检查点可在非终态（含外部取消留下的 `executing`）下续跑，不再强制要求人工兜底态 |
| 局部批次依赖 | 调度器接受 `prior_results`：续跑/返工批次只含未完成项时，已完成的上游依赖视为满足，避免被 DAG 校验拒绝后误触发重规划 |
| 成本控制 | 工具返回单字符串字段截断 12,000 字符；`code_agent` 嵌套回报截断 8,000 字符 |
| 评审可靠性 | 评审输出无法解析时做一次严格契约重试；调用超时不重试；耗尽后仍 fail-closed 并记录 `review_parse_error` |

### 14.3 复跑结果

同一模型、同一任务，探针外部观测上限 1800s：

| 运行 | 终态 | 墙钟 | 总 tokens | 模型调用 | 工具调用（失败） | 清单 |
| --- | --- | --- | --- | --- | --- | --- |
| `bench-20261103_rerun/run-1` | 外部取消（截断时产物已齐全） | 1800.02s | 572,395（输入 476,735 / 输出 95,660） | 57 | 8（2 失败） | 14 项全部通过 |
| `bench-20261103_rerun/run-2` | `completed` | **803.17s** | **326,037**（输入 278,533 / 输出 47,504） | 38 | 5（0 失败） | 14 项全部通过 |

run-2 分 Agent token：

| Agent | 调用 | tokens | 占比 | 生成耗时 |
| --- | --- | --- | --- | --- |
| `supervisor_agent` | 12 | 111,143 | 34.1% | 211.1s |
| `review_agent` | 7 | 59,774 | 18.3% | 175.8s |
| `code_agent` | 19 | 155,120 | 47.6% | 467.6s |

生产 token 台账覆盖率：run-2 为 100%（326,037/326,037）；run-1 为 96.7%（553,626/572,395），缺口来自外部取消时尚未收尾的生成调用。

run-1 超时原因（与设计缺陷的区分）：

1. 03:27:41 开始执行，03:52:37 进入汇总，执行阶段约 1496s；
2. st5 在 03:42–03:52 之间经历 2 次失败恢复（契约解析、沙箱）；
3. 结果评审于 03:54:35 要求 st3 返工，03:56:00 被 1800s 外部上限截断，截断时四件产物已齐全、清单全部通过；
4. 无进展看门狗未触发是**正确行为**——期间持续有子任务结果与检查点落盘；绝对兜底 2400s 尚未到期，是探针先截断。

### 14.4 断点续跑实测

- run-1 的检查点保留了 4 个成功子任务，仅 st3 未完成。
- 首次 CLI 续跑被拒绝：外部取消留下的检查点状态是 `executing`，原逻辑只接受 `human_required`；已放宽为“已恢复检查点 + 非终态”可续跑。
- 第二次续跑在 1062s 内完成，但触发了重规划并把 5 个子任务全部重跑，消耗 404,232 tokens。根因：续跑批次只含 st3，其已完成的上游 st1/st2 不在批次内，DAG 校验判为依赖缺失 → 误判分解问题 → 重规划生成新 ID、旧结果无法复用。
- 已修复：调度器支持批次外已完成依赖（`prior_results`），并新增调度器与续跑集成测试（72 项相关测试通过）。**该修复尚未用真实 LLM 再次复跑**，属于代码与测试层证据。

### 14.5 结论与剩余问题

1. **完成度**：两次复跑的产物清单都全部通过；run-2 在 803s 内正常完成，run-1 仅因外部观测上限被截断，不是产品超时失败。
2. **成本**：最好成绩 326,037 tokens，较 11-02 最佳 369,667 下降 11.8%，较 509,326 下降 36.0%；但最差分支仍达 572,395，成本方差没有消除。
3. **超时语义**：固定总时长无法治理“正常运行但耗时不可预测”的任务；无进展看门狗 + 检查点续跑才是主控，总时长只保留兜底职责。
4. **仍待解决**：结果评审返工与失败恢复仍可能把单次任务放大到 1800s 以上；续跑的局部依赖修复待真实 LLM 复测；外部取消路径的台账仍有约 3.3% 缺口。

### 15.5 结论

1. provisional 交付在真实模型下可以稳定走通“先交付 → 后台评审 → 通过收口”，且先行交付期间用户已拿到完整结果。
2. 后置校验与机检验收规则都由真实模型触发了实际分支，不是只存在于代码中。
3. 默认值保持保守：异步交付与评审并行默认关闭，`risk_based` 未启用；本轮没有用真实流量验证这些非默认路径。

### 15.6 11-04 调度动作接入工具路径实测

改造前：`PeriodicTaskPoller._run_task_action` 只用一次 LLM 调用执行 `schedule_spec.action`，无法写文件或运行命令。

改造后：到期动作经 `TaskRouter` 分类与选路——简单动作仍单次直答/推理；目标或验收标准要求文件、命令时，由确定性工具意图升级进入完整工作流。每个调度任务使用独立子沙箱 `<sandbox>/scheduled/<task_id>`，并发任务产物不互相覆盖；执行路由写入 `execution_route` 审计日志；动作非 `completed` 终态时保存检查点并暂停。到期动作若被分类为 `persistent_task`，会强制改走完整工作流，避免每次到期重复创建嵌套调度任务。

真实模型实测（同一模型、一次性调度任务，经 `_execute_task` 全链路）：

| 调度动作 | 判定 | 终态 | 产物与结果 |
| --- | --- | --- | --- |
| 在当前沙箱中创建文件 `scheduler-tool-check.txt`，内容写入 `SCHEDULER_OK`，并确认文件已创建。 | `full_workflow` | `completed` | 文件存在且内容为 `SCHEDULER_OK`，子任务回报 `verified=true` |
| 用一句话说明 1+1 等于几，不要写入任何文件。 | `direct_answer` | `completed` | 结果“1+1等于2。”，未启动工作流 |

实测中发现并修复分类器别名兼容问题：模型偶发输出 `"direct"` 而非 `direct_answer`，原逻辑判为非法并降级为完整工作流；现在对 `direct` / `deep` / `persistent` / `workflow` 等语义明确别名做归一化，未知取值仍保守降级。修复后第二个动作稳定走 `direct_answer`。

证据边界：真实运行验证了“需要工具 → 完整工作流 → 文件落盘”和“简单动作 → 直答”两条主路径；嵌套调度防护、检查点注入、独立沙箱与失败暂停由单元测试覆盖。
